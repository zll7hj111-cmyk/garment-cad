对 WildWind Pattern（野风帖）参数化服装 CAD 系统现有 UI 的全面评审与优化方案。覆盖范围：设计令牌体系、全部 20 个 UI 组件、导航架构、交互模式、可访问性、暗色模式一致性。基于源码走查 + 实际界面截图 + 已有设计稿交叉验证。

一句话结论：设计令牌体系基础扎实、组件架构优秀（CardBase 虚拟化三件套是工程亮点），但存在 P0 级色彩信号过载和 P0 级双重导航混乱两个架构级问题，以及 可访问性几乎空白的系统性缺陷。本次优化定位为「Endfield 2.1 演进」——保留骨架，收敛信号、补齐无障碍、统一细节。

核心优势（应保持）： (1) ThemeTokens 单源 42 色令牌 + QSS 生成器，变色只需改一处； (2) CardBase 模板方法 + ReadOnlySkeletonSpec 收敛了 5 类卡片差异，消灭复制粘贴； (3) VirtualCardList 视口物化 + 对象池，大数据量下性能有保障； (4) 三层色彩分离纪律（强调色 / 类型色 / 语义色）设计理念正确； (5) 等宽数字纪律保证拖动时布局零抖动。
必须修复（P0）： (1) 同屏可达 9+ 色相争夺注意力——信号黄 + 斑马蓝橙 + 4 piece 色 + 4 语义色； (2) 主窗口标签与面板悬浮窗构成镜像导航，syncPanelTabs 双向同步是技术债； (3) 可访问性：键盘 Tab 不可达删除按钮、屏幕阅读器不可见虚拟列表行、无 ARIA 等价物。

02Critical Issue: Color Signal Overload (P0)

这是当前 UI 最严重的架构级问题。同一屏幕上同时出现过多竞争色相，用户无法建立稳定的「颜色 → 含义」映射。

问题本质：斑马纹蓝（#2F6FED）与 piece4 钴蓝（#2563EB）视觉重叠；斑马纹橙（#F59E0B）与 warning 琥珀（#B45309）同族易混淆。加上信号黄作为唯一强调色被稀释——用户看到黄色不再能确定它代表「当前激活」。

2.2 Proposed Solution: Two Options

Option A — Row bars encode card type (recommended)

竖线从「装饰性斑马纹」升级为「类型图例」。变量卡 = piece1 碳灰、公式卡 = piece2 深青、测量卡 = piece3 陶土、关联卡 = piece4 钴蓝。与页签颜色呼应，形成一致的颜色语言。

  • 优点：增加信息密度不增加认知负担——颜色已有含义（类型），只是复用到竖线上
  • 优点：消除斑马纹蓝橙两个多余色相，同屏色相从 9+ 降到 7
  • 优点：页签下划线已用 piece 色（PanelSubTabBar 实现），竖线与之呼应形成闭环
  • 代价：需要用户拍板确认（当前斑马纹是历史决策）
  • 实现：CardBase::paintEvent 左竖线色从固定蓝橙改为 m_pieceColor 成员

Option B — Neutral zebra stripes

彻底退出色彩信号层：偶数行用中性灰 #CBD2DC，奇数行无色（仅靠 surface3 条纹底区分）。最保守方案。

  • 优点：零风险，不影响任何现有色彩语义
  • 缺点：丢失一个可利用的信息通道（竖线本可用于编码类型）
  • 缺点：中性灰辨识度低，尤其在暗色模式下
  • 适用：如果团队希望最小改动范围

  • 消除 syncPanelTabs：主窗口标签只控制面板显隐，不再需要双向同步状态。

05Accessibility Audit (Systemic Gap)

这是评分最低的维度（C-）。Qt Widgets 应用天然支持部分辅助技术，但当前实现中有意或无意地阻断了多个关键路径。

5.1 Accessibility Checklist

  • Text contrast meets WCAG AA (4.5:1 minimum) for all token-defined text colors
  • Focus visible on form inputs (QSS :focus-outline via Fusion style)
  • Keyboard navigation works for main form elements (Tab through inputs)
  • Tooltip text available on hover (400ms delay, no animation per Ela discipline)
  • Touch targets: Most interactive elements ≥ 24px, but some tool buttons are 26×26 (barely passing). Delete buttons are 20×20 (below minimum).
  • Screen reader labels: ElaToolButton icons have accessible names via ElaIconType, but custom painted elements (card left bars, ghost delete slots) have none.
  • Dark mode: All surfaces checked for light-island failure. Text readability maintained. But some hardcoded colors in LayerPanel won't switch.
  • Error identification: Formula evaluation errors show red text + tooltip, but no programmatic error association (accessible description missing).
  • VirtualCardList not accessible: Rows outside viewport are not in widget tree → screen reader cannot see them. Only ~8-10 rows are "visible" to assistive tech regardless of actual list size.
  • Delete button not keyboard reachable: setVisible(false) until hover means Tab key can never focus it. No alternative keyboard method to delete a card.
  • No ARIA-equivalent roles: Qt accessibility framework exists (QAccessible) but no custom roles registered for cards, lists, or badges.
  • Color-only information: Piece type indicated solely by left bar color. Color-blind users cannot distinguish variable vs formula vs measure cards.
  • No reduced-motion support: ElaWidgetTools animations removed (good), but CanvasView rendering has no prefers-reduced-motion check.
  • Drag-and-drop no alternative: Formula card reordering requires mouse drag. No keyboard equivalent (no arrow-key reorder mode).

Different hues! User's "formula = teal" memory breaks.

Proposed fix: Dark mode piece colors should keep the same hue, only adjusting lightness. Example: piece2 deep teal #0F766E → brightened to #2DD4BF (same hue, higher luminance). This preserves cross-mode type recognition. The current dark palette uses completely different hues (slate-blue-gray instead of carbon, etc.) which forces users to relearn color meanings when switching themes.

6.2 Other Dark Mode Issues

  • LayerPanel hardcoded colors (#2E86C1, #B0BEC5, #7F8C8D): These do NOT change in dark mode. Eye icon stays medium-blue on dark background (OK-ish visibility), but closed-eye gray #B0BEC5 may fail contrast on dark surface2.
  • ChipLabel border (#4E5866 / #9AA4B2): Two separate hardcoded values for light/dark — this is actually a manual fork that happens to work, but should be tokenized.
  • tooltip_shot.png:> The tooltip shown uses light-background styling even though we can't tell from the screenshot whether it was captured in light or dark mode. Tooltip tokens exist and should handle both correctly.

08Design Principles (Endfield 2.1)

  1. One accent color. Signal yellow #FFDE00 is the sole "action/selected/focus" signal. Maximum one solid-yellow element per screen. All other colors are entity identity (piece) or semantic state only.
  2. Three color layers, never mixed. Accent (yellow, 1 active instance) → Piece type (4 identity colors) → Semantic (4 status colors). A color never serves two roles.
  3. One navigation path. Main window tabs = panel show/hide toggle only. Panel internal tabs = content classification. No mirrored navigation, no bidirectional sync.
  4. Paper and ink. Canvas = blueprint-gray paper. Panels = white binder with hairline borders. Right angles by default, functional radius ≤ 4px.
  5. Numbers don't jitter. All readouts/inputs use monospace font with fixed column width. Layout zero-displacement on value refresh.
  6. Density serves the hand. CAD is a high-frequency tool: information density takes priority over whitespace aesthetics. But every interactive target ≥ 24px height.
  7. Accessibility is not optional. Every visual signal must have a non-color backup. Every action must be keyboard-reachable. Screen readers must understand the interface.
  8. Zero hardcoded colors. Every pixel of color comes from ThemeTokens. If you need a new color, add a token first.
